# Implementation Readiness Audit

Chinese mirror: `implementation-readiness-audit.zh.md`.

## Conclusion

The v0.9.1 test plan is ready for implementation review, but the codebase does
not yet contain the full `complete-worldengine-validation-suite` runner.

Reusable existing capabilities:

- Validation Client already discovers WorldEngine health/capabilities.
- Validation Client already has older validation-run and `operation-log.jsonl`
  export APIs.
- The existing v0.8/v0.9 E2E can export a structured blocked handoff when
  WorldEngine is unreachable.
- Evidence bundles already have a named-artifact and redaction-status
  foundation.

Current gaps:

- No `complete-worldengine-validation-suite.spec.ts`.
- No E2E-local recorder for step-by-step `operation-log.jsonl`,
  `api-log.jsonl`, `console.log`, `transcript.md`, and screenshots.
- The existing backend operation-log schema does not include v0.9.1 fields such
  as `step_id`, `before`, `after`, `api_refs`, `artifact_refs`, and `result`.
- The current blocked handoff may write an empty `operation-log.jsonl`, which
  does not satisfy the requirement that every executed operation is recorded.
- Existing E2E coverage targets the v0.8/v0.9 handoff, not the Phase 1-4 Agent
  autonomous operation script.
- `SCENARIO_REQUIRED_ARTIFACTS` does not yet define
  `complete-worldengine-validation-suite` separately.

The first implementation should add test assets and E2E result-directory
generation before deciding whether backend schema expansion is needed. The
first v0.9.1 runner can generate the required rich artifacts inside the
Playwright result directory. The backend operation-log endpoint can remain an
app-internal log source, but it is not enough as the sole v0.9.1 step evidence.

## Implementation Strategy

### Layer 1: E2E-local authoritative evidence

The primary evidence for `complete-worldengine-validation-suite` should be
generated by the E2E runner in its own result directory:

```text
apps/web/e2e/support/operationRecorder.ts
apps/web/e2e/support/completeSuiteResult.ts
apps/web/e2e/complete-worldengine-validation-suite.spec.ts
```

Rationale:

- The Playwright runner is the source of truth for what the Agent clicked,
  typed, waited for, downloaded, and saw.
- Backend operation logs are app event logs; they do not naturally know
  Playwright screenshots, waits, downloads, phase verdicts, or blocked steps.
- Direct API harvest must be separated from UI operations. The E2E-local
  recorder can write API harvest into `api-log.jsonl` instead of disguising it
  as UI behavior.

### Layer 2: Validation Client API evidence

The E2E runner may still call Validation Client APIs for supplemental evidence:

- `/health/worldengine`
- `/sessions`
- `/sessions/{session_id}/evidence/bundle/manifest`
- `/sessions/{session_id}/evidence/bundle/artifacts`
- `/validation-runs/{run_id}/operation-log.jsonl`
- `/validation-runs/{run_id}/api-summary`

These responses are supplemental evidence. They must be written to
`api-log.jsonl`, and `transcript.md` must identify them as direct evidence
harvest rather than user clicks.

### Layer 3: later backend schema enhancement

If users later need to download the v0.9.1 rich result directory directly from
the UI, expand:

- `apps/api/app/routes/evidence.py`
- `apps/api/app/routes/validation_runs.py`
- `apps/web/src/api/client.ts`
- `apps/web/src/components/RuntimeConsole.tsx`

This is not a prerequisite for the first v0.9.1 runner. The minimum v0.9.1 goal
is an Agent autonomous test that generates a complete result directory for
second-Agent review.

## File-Level Implementation List

### `apps/web/e2e/support/operationRecorder.ts`

Must provide:

- `createOperationRecorder(options)`
- `recordOperation(entry)`
- `recordApiCall(entry)`
- `recordScreenshot(stepId, phase, page, name)`
- `recordTranscript(section, lines)`
- `writeAll()`
- `redactText(value, options)`
- `scanForBlockingMarkers(files)`

Minimum behavior:

- Generate incremental `api-log:0001` and `operation-log:0001` refs.
- Each operation must include `step_id`, `phase`, `operation_kind`, `target`,
  `before`, `after`, `api_refs`, `artifact_refs`, `result`, and `timestamp`.
- Each API record must include `source_step_id`, `method`, `url_origin`,
  `path_template`, `request_summary`, `response_summary`, and `duration_ms`.
- Run redaction scanning before writing files.
- If redaction fails, still write the result directory, but force final status
  to `fail`.

### `apps/web/e2e/support/completeSuiteResult.ts`

Must provide:

- `createCompleteSuiteResult(options)`
- `markStepPlanned(stepId)`
- `markStepExecuted(stepId, refs)`
- `markStepBlocked(stepId, reason)`
- `writeCoverageMatrix()`
- `writeApiSummary()`
- `writeResultJson(status)`
- `writeCommandMatrix(commands)`
- `writeCompatibilityArtifacts()`

Minimum behavior:

- Output structured `BLOCKED` when WorldEngine is unreachable.
- Output phase-level `BLOCKED` when a capability is missing while preserving
  evidence for already executed steps.
- Never output `pass` when a required artifact is missing.
- `result.json.status` must be one of `pass`, `partial`, `blocked`, or `fail`.

### `apps/web/e2e/complete-worldengine-validation-suite.spec.ts`

Must execute in order:

1. Phase 1: open page, discover connection, create world, run 5 ticks, download
   basic evidence.
2. Phase 2: run 20 ticks, pause/resume/single tick, inspect events/snapshots/
   branch, submit two natural-language directions.
3. Phase 3: inspect Agent public state, Agent step/observe, run 30 observation
   ticks, inspect memory summary, consolidation, narrative projection, and
   diagnostic dialogue.
4. Phase 4: export full result directory, redaction scan, WorldEngine checker
   handoff, second-Agent review placeholder.

When a UI control or WorldEngine capability is missing:

- Write a blocked entry to `operation-log.jsonl`.
- Write a blocked entry to `coverage-matrix.json`.
- Explain the blocker in `transcript.md`.
- Continue closeout instead of throwing before the result directory is written.

### `apps/web/src/__tests__/operationRecorder.test.ts`

Must cover:

- UI click/fill/wait/download/screenshot operation entries.
- Blocked operation entry.
- API log entry.
- API summary aggregation.
- Redaction failure.
- Every JSONL line is parseable.

### `apps/web/src/__tests__/completeSuiteResult.test.ts`

Must cover:

- WorldEngine unreachable blocked result.
- Missing-capability phase blocked result.
- Missing artifact prevents pass.
- Redaction failure forces fail.
- Coverage matrix maps every planned step.

## Minimum Acceptance

After implementation, even when WorldEngine is unreachable, the run must produce:

```text
validation-runs/<timestamp>-complete-worldengine-validation-suite/
  result.json
  coverage-matrix.json
  command-matrix.md
  operation-log.jsonl
  api-log.jsonl
  api-summary.json
  capability-discovery.json
  redaction-report.json
  console.log
  transcript.md
  screenshots/
```

And:

- `operation-log.jsonl` includes at least `P1-01 page_open`,
  `P1-02 connection check`, a blocked phase verdict, and closeout export.
- `api-log.jsonl` includes at least health/capability discovery requests.
- `result.json.status=blocked`.
- `redaction-report.json.status=pass` or a real fail.
- The E2E process may pass, but the validation conclusion is `BLOCKED`, not
  `PASS`.
